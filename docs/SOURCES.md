# Chord experiment audio

Chord mode also includes a separate [attack/decay strike detector](ATTACK_DECAY.md) with its own training data and fixed analysis settings.

In the lab, select **Chord mode** and start the microphone. Percentages under the keys are relative fitted strengths. **Calibrate** uses the existing single-note A4 prompt and applies the saved reference to the entire dictionary.

The **β divergence** slider runs the multiplicative update in Equation 12 for β from 0 to 2. **Window** selects Hann, Hamming, Blackman, or Kaiser with shape parameter 4. The Kaiser shape is independent of the fitting slider. All four use 50 ms of audio, 10 ms hops, and a zero-padded 2,048-point FFT with a 10 Hz grid. **Calibrate keys** builds templates for all four windows and saves the isolated strike for attack/decay training. Earlier personal Hann templates are interpolated onto the new grid. [Dessein et al., Equation 12](https://archives.ismir.net/ismir2010/paper/000083.pdf#page=3)

**Guided microphone test** previews each trial and waits for you to press **Record**. Release the keys and pedal during the one-second lead-in, then play when the prompt changes. After the release cue, the next trial waits for another press. The app saves a WAV and JSON under the app’s user data folder in `guided-chord-tests`. The JSON includes β, window, tuning, active personal templates, timestamped prompts, and per-window raw gains, detected notes, input levels, and analysis times, with trial numbers. Sample indices refer to the WAV, which contains only the recorded portions. Use the WAV to locate the actual keystroke before measuring latency. Guided recording tries to retain the 10 ms analysis cadence and counts skipped analysis hops and discarded mic frames separately.

**Replay test** stops the microphone and feeds labeled audio directly to the same detector at A4 = 440 Hz. The first result per case is the elapsed audio time until three consecutive 10 ms updates contain exactly the expected keys. The second result is the percentage of exact updates during the 500 ms target segment. The replay runs silently and restores your tuning afterward.

During ordinary live play, Godot sends the newest audio window to a worker thread for the FFT and β fit. The worker keeps one pending window and replaces it if fresher audio arrives. The main thread reads the most recent result when updating the display. Guided recording and replay process their windows in order so their results can be matched to the captured audio.

The four window-specific dictionaries are adapted from **Salamander Grand Piano** by Alexander Holm, distributed by Tone.js under CC BY 3.0. The source piano is a Yamaha C5 sampled in minor thirds. Each column uses the closest sampled key, transposed as needed, with five short magnitude spectra averaged and quantized. [Original recordings and attribution](https://github.com/Tonejs/audio/tree/master/salamander) · [License](https://creativecommons.org/licenses/by/3.0/)

`chord/templates/replay.wav` is a labeled mix of **MS Basic** piano recordings from a separate bank. The supplied license and credits accompany this file in [MS-Basic-LICENSE.txt](../chord/templates/MS-Basic-LICENSE.txt). The recordings were trimmed, level-matched, mixed, and faded. The lowest pair and highest key are pitch-shifted fixtures. The ringing-C4 case overlaps recordings to simulate sustain. These fixtures measure algorithm behavior with known labels. They do not measure a phone's acoustic latency.

To regenerate, decode the Salamander clips at MIDI keys 21, 24, …, 108 to mono 44.1 kHz float32 little-endian files named `<midi>.mp3.f32`. Decode the left MF channel from the MS Basic recordings to `mf-<midi>.ogg.f32` at the same rate. Supply the first three seconds, or the full clip if shorter. From the project root run `node tools/build_chord_assets.mjs <decoded-directory>`.
